# 飞书多维表交付规范（投递清单主交付面）

## 1. 写入前的对象和字段检查

先解析 Base URL、app token、table ID、view ID，读取真实字段名/类型、记录总数和最近批次。追加任务只使用现有表，不新建表、不删除历史记录；已有 `批次` 字段时按批次区分本次写入。

目标字段顺序（若现有表有额外字段，保留但不擅自写入）：

`公司 | 投递岗位 | 城市 | 届别/学历要求 | 校招官网链接 | 专岗详情链接 | JD截图 | 投递日期 | 投递人 | 投递截图 | 匹配度 | 匹配证据 | 主要缺口 | 核验时间 | 截止时间 | 优先级 | 相关性 | 企业性质 | 所属行业 | 面试状态 | 笔试状态 | 投递进度 | 求职备注 | 备注`

本次岗位同步的写入白名单为：公司、投递岗位、城市、届别/学历要求、校招官网链接、专岗详情链接、JD截图、匹配度、匹配证据、主要缺口、核验时间、截止时间、优先级、相关性、企业性质、所属行业、备注，以及现有表已定义的批次列。投递日期、投递人、投递截图、面试状态、笔试状态、投递进度、求职备注保留原值，除非用户本轮明确要求更新。

只填主字段列，勿碰重复列、历史跟踪列、公式列或无授权字段。字段名以 API 读回为准，不以 Markdown 示例猜测。

常用类型码：文本 `1`、单选 `3`、多选 `4`、日期时间 `5`、附件 `17`。建字段前先确认真实表中不存在同名字段；附件字段创建不要传 `property`。主字段改名时使用 `PUT /fields/{field_id}` 并带上 `type`。

## 2. 权限和身份前置

应用 tenant token 直调 OpenAPI。必须同时满足：

1. 开放平台已开通 `bitable:app` 并创建版本、发布；
2. 多维表文件分享面板已把应用（`member_type=appid`）加为可编辑协作者，权限读回应为 `full_access`。

CLI 的 `--as user` 若返回 131006，不要重复重试；换用应用 tenant token。每次长批次开始前重新获取 token，避免过期。

## 3. 串行分批写入

- 单批 ≤200（即“单批≤200”）；本流程按 15–25 条一批准备，批次之间串行执行，遇到 1254291 只退避并重试未完成批次。
- 写入前按 `公司 + 投递岗位（含职位 ID）+ 城市 + 届别/批次` 与已有非空记录去重；已有记录计入公司上限，已有 3 条的公司本批不再新增，已有 1–2 条时只补足剩余名额；重复项不更新、不删除，记入去重报告。
- `batch_create` 只发送写入白名单字段；`batch_update` 只发送本批明确变更的字段，不把整行空值覆盖回去。
- 多选城市用数组，单选用字符串，日期时间用 `YYYY-MM-DD HH:mm:ss`；核验时间字段按 `YYYY-MM-DD` 文本写入，例如 `2026-10-15`。
- 批次成功后独立回读本批记录数和关键字段，确认无重复、无空主字段，再继续下一批。

写记录示例端点：

```text
POST /open-apis/bitable/v1/apps/{app}/tables/{table}/records/batch_create
POST /open-apis/bitable/v1/apps/{app}/tables/{table}/records/batch_update
```

如确需补建字段，使用 `POST /open-apis/bitable/v1/apps/{app}/tables/{table}/fields`，body 至少包含 `field_name` 和 `type`；补建前必须获得本轮明确授权，不能用补字段绕过“只填主字段列”。

## 3.1 存量表全量复核与修正

任务要求复核已有表时，分页读取全部记录（包括约 300 条规模），逐条保留 `record_id` 和原字段快照。问题清单至少包含：`record_id`、公司、岗位、问题类型（方向/链接/有效期/限生源/重复/空字段）、证据或原链接、建议动作、处理状态、核验时间。

用户明确授权后，才可对问题清单执行 `batch_update` 改链接或删除记录；删除需用户明确授权。删除前保存待删 `record_id`、原字段、证据和原因，改链接前重新核验详情直达/官方入口/平台入口。没有合格替代链接时清空详情字段并写“官方系统·岗位名·需登录系统内搜索”，不能用主页或聚合页顶替。

复核修正后导出 `utf-8-sig` 复核清单 CSV，并再次分页拉全量记录，核对复核前后有效记录数、删除/更新/未变更 `record_id`、问题残留、重复数、链接分布和未授权字段。只回读修改行不算全量验收。

## 4. 链接与截图字段

- `专岗详情链接` 只能放详情直达 URL；不能把公司主页、聚合页或列表页复制进去。
- `校招官网链接` 放官方列表入口；平台入口需在“备注”写明平台和“需登录/二次确认”。无链接时两个字段留空，备注写“官方系统·岗位名·需登录系统内搜索”。
- HTTP 200、页面打开或 CLI success 都不等于岗位可投递；回读验收要检查页面可见岗位、列表可搜索和投递入口证据。
- JD 截图按 `公司-岗位.png` 映射。多条命中、无命中、文件名与岗位不一致都必须报告，不允许静默错配；失败检索保留 `公司-核验项-无结果（证据）.png`。

附件上传：

```text
POST /open-apis/drive/v1/files/upload_all
parent_type=bitable_file, parent_node={app_token}
```

附件 CellValue 使用 `[{'file_token': '...', 'name': '公司-岗位.png'}]`；创建附件字段时不要传 `property`，避免 `1254088 AttachFieldPropertyError`。

## 5. 视图顺序

先用 `GET /open-apis/bitable/v1/apps/{app}/tables/{table}/views?page_size=50` 读真实 view ID，再用 base/v3：

```text
PUT /open-apis/base/v3/bases/{app}/tables/{table}/views/{view_id}/visible_fields
body: {"visible_fields": ["公司", "投递岗位", "城市", "届别/学历要求", "校招官网链接", "专岗详情链接", "JD截图", "匹配度", "匹配证据", "主要缺口", "核验时间", "截止时间", "优先级", "相关性", "企业性质", "所属行业", "备注"]}
```

数组只包含需要展示的真实字段名；不要用 bitable/v1 的旧视图更新端点，也不要为了排序创建重复字段。

## 6. 独立回读验收

写入完成后重新拉全量记录（分页 `page_token`），把“有效记录”定义为主字段和投递岗位均非空，不用固定数量判断成功。至少核对：

- 实际写入数 = 本批成功数，累计数 = CSV 有效行数 − 已去重/剔除行数；
- 每条公司、岗位、城市、届别/学历、匹配证据、主要缺口、核验时间、截止时间完整；
- 详情直达/官方入口/平台入口分布与 CSV 一致；
- JD 截图附件存在且文件名与公司/岗位一一对应；
- 同一学生同一公司不超过 3 条，已有记录计入公司上限，新增记录与已有记录零重叠；历史超额记录只报告，不删除；
- 只写入主字段列，重复列、公式列、历史跟踪列未被改动；
- `Open`、剔除原因、无对口和数量缺口已进入备注或交付汇报。

不能用 200、revision 增加、total 增加、静态截图或“保存成功”提示代替独立回读。

## 7. 常见错误

| 错误/现象 | 处理 |
|---|---|
| 403 / 91403 | 检查 `bitable:app` 发布状态和文件分享面板的应用可编辑协作者 |
| 1063004 | 应用不是文件协作者；先补文件级权限 |
| 131006 | user 身份无权访问；改用 tenant token |
| 1254088 | 附件字段创建时移除 `property` |
| 99992402 | 字段更新 PUT 带上 `type` |
| 404 visible_fields | 使用 `base/v3` 端点并核对 view ID |
| 1254291 | 串行写入，退避后只重试未完成批次 |
| 记录全 null 但 total 增加 | 只统计主字段非空有效记录，不触碰其他用户空记录 |
