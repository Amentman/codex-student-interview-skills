# 校招岗位匹配与核验细则

## 1. 开工前输入与届别口径

| 项 | 必填 | 解析与记录 |
|---|---|---|
| 毕业年份/届别 | 是 | 记录毕业月份；提前毕业（如 2026.12）不强行归入普通届别，届别记 `Open` |
| 学历/专业 | 是 | 本科/硕士/博士、专业及学校；只用于匹配，不替代岗位硬性要求 |
| 目标方向 | 是 | 先映射到白名单，再生成检索词；不把“AI”单独当成方向 |
| 目标城市 | 是 | 多选；每条岗位记录命中城市和不匹配原因 |
| 全职/实习 | 是 | 校招全职优先；实习占比按用户约定控制在 5–15% |
| 明确限制 | 否 | 不接受的城市、行业、公司、生源或投递方式，属于硬过滤 |

开工还要读取已有飞书表的公司、岗位、城市、届别/批次和职位 ID，形成去重键；已有记录不删除、不覆盖，新增批次只追加未重复岗位。

若任务明确要求存量表全量复核（可达 300 条），改用“复核模式”：分页读取全部记录，保留每条 `record_id`，逐条检查方向、链接、有效期、生源、重复和空字段，输出逐条问题清单，不用抽样代替全量。

## 2. 方向硬过滤

### 2.1 白名单

- 产运：产品、产品运营、用户、内容、电商运营；
- 数据分析（业务向）；
- 数据产品；
- 市场、营销、品牌；
- 管培，但只保留产品/市场/运营方向。

### 2.2 严禁方向

算法（NLP/CV/推荐/LLM）、前后端/客户端/嵌入式开发、测试、运维、安全、数据开发/数仓/ETL、ML 工程、AI 应用开发、投行/审计/投资均剔除。

岗位名带“研发/工程师/开发/算法”时，必须打开 JD 判断实际职能；确认研发就剔除，职责边界不清也剔除。不得因为岗位名同时出现“产品、运营、平台、AI”而放宽规则。

## 3. 证据账本与匹配判断

| 级别 | 含义 | 允许的写法 |
|---|---|---|
| `Confirmed` | 简历正文中学生本人做过的动作、责任和结果 | 可写入匹配证据；指标要保留口径和来源 |
| `Externally verified` | 官方列表/详情页或可追溯官方公告核验到的岗位信息 | 可写岗位名称、城市、届别、学历、截止和职能 |
| `Inferred` | 从 Confirmed 证据推导的迁移能力 | 只能写“可迁移/待验证”，不能改写为学生经历 |
| `Knowledge supplement` | 公司、行业或岗位背景补充 | 不能证明学生贡献或岗位仍在招 |
| `Open` | 未确认、页面不可检索、职责/届别/学历未明确 | 必须写入主要缺口或备注，不得冒充可投递 |

每条记录必须同时填写“匹配证据”和“主要缺口”。匹配度按方向、JD 核心要求、届别/学历、城市四维判断：方向对口且核心要求有 Confirmed 证据才可评“高”；相邻可迁移为“中”；只有兴趣或泛关键词为“低”。

## 4. 有效期与可投过滤

以实际核验日为准（本轮示例日期：`2026-10-15`）：

1. 截止日期早于核验日：剔除，原因写“已过截止”；
2. 页面显示下架、无岗位、搜索无结果或投递按钮失效：剔除，原因写“已下架/不可投”，并保留证据截图；
3. 限定不符合学生的生源、身份、毕业窗口、学历、城市或内部推荐：剔除，原因写清具体限制；
4. 未公布截止：保留为“截止未公布（Open）”，不猜日期；
5. 只有公告或第三方转载、无法在官方系统定位岗位：不得作为 Confirmed 可投岗位，最多作为 Open 线索。

## 5. 链接三级策略（以“点开能投递”为验收口径）

| 级别 | 记录方式 | 验收要求 |
|---|---|---|
| 1. 详情直达 | 写入“专岗详情链接” | URL 打开即该岗位 JD，页面可见岗位名称/ID，能进入投递或提交入口；不能只看 HTTP 200 |
| 2. 官方校招入口 | 写入“校招官网链接” | 入口为公司官方校招列表（如 `campus/jobs`、`hotjob`、`10086` 校招、iguopin 公司页），进入后能搜索到该岗位；备注写搜索路径 |
| 3. 平台入口 | 无独立平台列时写入“校招官网链接”，并在“备注”标明平台；“专岗详情链接”留空 | 国聘、Offer先生、智联托管等平台页必须能定位岗位；平台不是官方详情，备注“平台入口·需登录/二次确认” |

无可用链接时：两个链接字段留空，备注统一写“官方系统·岗位名·需登录系统内搜索”。

严禁把公司主页、集团主页或聚合页冒充详情链接（公司主页/聚合页冒充详情），例如 `iguopin company?id=...` 不能替代 `job/detail?id=...`。详情链接缺失时留空，不把列表页复制进详情列。

## 6. 核验 SOP 与截图

1. 从公司官方校招入口进入列表，搜索岗位名、职位 ID、城市和届别；再打开详情页。
2. 记录岗位名、ID、职能、城市、届别/学历、截止原文、投递按钮/状态和核验日期。
3. SPA/JS 页面使用浏览器渲染；详情仍不能定位时标 `Open`，不能用猜测 URL 补齐。
4. 成功或失败都保留证据截图：成功为 `公司-岗位.png`；无结果为 `公司-核验项-无结果（证据）.png`。截图不能伪造岗位存在。
5. 记录链接级别和核验结果；详情直达、官方入口、平台入口不得混写。

## 7. 去重、批次与公司上限

- 去重键：`公司 + 投递岗位（含职位 ID）+ 城市 + 届别/批次`；同一岗位不同入口仍视为一条。
- 每公司最多 3 个岗位，已有记录计入公司上限。先把已有记录与本轮候选合并并排序，再运行 `scripts/enforce_company_cap.py`；已有 3 条时本轮不新增，已有 1–2 条时只补足剩余名额，第 4 条起从最终清单和飞书写回剔除，`dropped` 保留公司、岗位和原因。
- 每批准备 15–25 条，校招全职优先，实习控制在 5–15%；单次 API 不超过 200 条并串行写入。
- 与已有表零重叠；历史公司超额记录只报告和去重，不删除历史数据。已有 3 条记录的公司不得因后续搜索再次突破上限。
- 对口岗位不足时如实写数量缺口和“无对口”公司，不用研发/算法或过期岗位凑数。

## 8. 交付汇报必含项

- CSV 编码为 `utf-8-sig`，飞书写入批次和实际成功数量；
- 详情直达/官方入口/平台入口的数量分布；
- 已过截止、已下架、限生源/不可投、疑似研发和公司上限剔除清单；
- `Open` 项（届别、截止、投递入口、职责等）和需学生操作的二次确认；
- 实际岗位数与目标 15–25 条的数量缺口；
- 每条核验日期和主要证据来源。

复核模式还必须报告：复核前后有效记录数、删除/更新/未变更 `record_id`、每类问题数量、残留问题和全量回读结果。用户明确授权后才可在表内执行删除/改链接；删除需用户明确授权，并先保存待删 `record_id`、原值、证据和原因。
