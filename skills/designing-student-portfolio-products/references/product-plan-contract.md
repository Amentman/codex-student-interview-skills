# 学生作品集产品方案合同

为新方案、方案审阅或已有 Demo 补全时使用。按实际任务压缩篇幅，但不得省略会改变真实性、开发范围或验收结论的字段。

## 四步交付映射

| 步骤 | 必须产出 | 进入下一步的门槛 |
|---|---|---|
| 1. 前置资料 | 筛选后的资料、学习顺序、工具小任务和完成标准 | 学生知道先学什么、做什么、怎样证明做过 |
| 2. 完整 PRD | “完整 PRD 十二槽位”全部填写 | 方向、闭环、架构、字段、边界、学生执行任务和非目标已锁定 |
| 3. UI/UX Demo | 第 5 节全部页面、状态与主流程的可操作原型 | 学生能按界面和交互基线进入开发 |
| 4. 验收标准 | 第 8–9 节的检查项、提交证据、通过条件与 `Open` | 学生知道做完后提交什么、导师如何判断通过 |

## 责任分工

- Agent 负责调研、方向判断、规划包、PRD、UI/UX Demo、学生执行任务和验收标准。
- 学生负责学习、样本准备、Prompt 迭代、代码开发、真实调用、调试、测试、Bad Case、复测、README 和现场讲解。
- 导师或 Agent 只有在学生提交真实产物后，才能按验收标准检查并记录通过/不通过；规划阶段不得预写完成结论。

## 完整 PRD 十二槽位

第二步的成品按以下顺序交付。每个槽位都要有正文、表格或图，不用散落的建议代替：

1. **执行摘要**：推荐产品、目标岗位、学生承接依据、核心产物、当前阶段和结论。
2. **事实账本**：`Confirmed`、`Externally verified`、`Inferred`、`Knowledge supplement`、`Open` 及来源。
3. **岗位与产品定位**：目标岗位/JD、用户、场景、问题、现状流程、目标流程和价值假设。
4. **范围合同**：MVP、非目标、周期、依赖、风险、公开/脱敏/模拟数据边界。
5. **业务闭环**：从来源输入到业务产物、人工复核、反馈回填和 Bad Case 复测的完整流程图。
6. **产品架构**：功能模块、模块职责、相互关系和主要入口；用架构图或结构树表达。
7. **页面与状态流**：页面地图、每页任务/输入/操作/输出/下一步，以及正常、空、错、加载、待复核和失败状态。
8. **数据与字段字典**：对象关系、关键字段、类型、来源、必填性、示例、枚举状态、引用与版本规则。
9. **处理与责任边界**：规则、AI、人工分别负责什么；Prompt/结构化 JSON、来源引用、导出/发布阻断条件。
10. **技术架构**：前后端、SDK/API/MCP/本地服务、数据流、鉴权、保存/导入导出、日志、超时、重试、降级与成本选型。
11. **学生执行计划与提交包**：从 UI/UX 到开发测试的节点、学生/导师责任，以及学生需要提交的源码、README、数据、Prompt 和演示材料。
12. **验收矩阵与 `Open`**：逐条成功标准、所需证据、当前状态、负责人和仍需补充的最小信息。

完整 PRD 的结构性检查是：十二槽位全部存在；产品架构、技术架构和数据流不是同一张图换标题；字段与状态足以支持 UI 和开发；每条验收能对应具体证据。

## 1. 先给结论

开头用一页以内回答：

- 推荐做什么产品，服务哪个目标岗位；
- 为什么它承接学生真实经历；
- 核心用户、单一场景和核心业务产物；
- 第一版多久能做、明确不做什么；
- 当前是构想、PRD、UIUX、开发中还是已验收。

## 2. 证据与适配

| 字段 | 内容要求 |
|---|---|
| 学生事实 | `Confirmed` 动作、工具、数据、职责与结果；附来源 |
| 目标岗位 | 当前 JD 或明确标注的代表性岗位画像 |
| 可迁移证据 | 学生事实怎样支撑该产品中的具体任务 |
| 差距 | 目前缺少的业务、产品、数据、AI 或工程能力 |
| 边界 | 公开数据、模拟数据、AI 生成、推断和 `Open` |

不能把课程目标、老师示例、JD 要求、公开行业数据或计划功能改写成学生经历。

## 3. 业务闭环

用一张流程图或表讲清：

```text
来源/输入
  → 样本清洗与标签
  → 规则或模型处理
  → 带来源的中间判断
  → 人工复核与修改
  → 可直接使用的业务产物
  → 测试/业务反馈
  → Bad Case、规则或 Prompt 修正
```

每个节点至少定义：责任人、输入、动作、输出、证据、异常、下一状态。最终产物要进入真实工作流，例如 Brief、分析卡、脚本、诊断报告、内容包或决策草案；不能停在聊天回答或漂亮图表。

## 4. 产品范围

### MVP

- 一个明确用户；
- 一条可演示主流程；
- 一个核心业务结果；
- 10–30 条有来源和字段说明的小样本即可起步；
- 正常、异常和边界输入；
- 至少 3 个 Bad Case 及复测记录。

### 默认不做

除非直接解决当前问题，否则不加入账号体系、权限系统、数据库、自动爬虫、自动发布、向量库、RAG、多 Agent、复杂部署或虚构的平台接口。

## 5. 页面地图与交互合同

页面名称随业务变化，但至少覆盖：

| 区域 | 核心内容 | 必须可见的状态 |
|---|---|---|
| 项目/任务定义 | 用户、目标、范围、数据边界、禁区 | 未完成字段、范围提示 |
| 来源/样本库 | 原始输入、来源、日期、标签、选择状态 | 空、无效、重复、模拟标识 |
| 处理/洞察 | 规则或 AI 结果、引用、置信边界 | 加载、超时、解析失败、待确认 |
| 业务产物编辑 | 可编辑结果、版本、人工修改 | 未保存、已修改、导出阻断 |
| 复核与风险 | 事实、合规、预算、发布等人工决定 | 待复核、通过、驳回、理由 |
| 测试与复盘 | 测试输入、结果、Bad Case、改动、复测 | 未测、失败、通过、`Open` |

首屏先让面试官看懂“谁在解决什么问题、当前证据来自哪里、下一步能做什么”。桌面端可采用固定流程导航、当前工作区、来源/风险侧栏；视觉方向应贴合业务，而不是套通用聊天框。

## 6. 数据对象

按业务裁剪，但至少能表达以下关系：

```text
Project
├─ StudentEvidence[]
├─ SourceSamples[]
├─ ProcessingRuns[]
│  └─ Findings[] → sourceIds[]
├─ Artifacts[] → findingIds[]
├─ ReviewDecisions[]
├─ TestCases[]
└─ BadCases[] → change → retest
```

关键字段包括：ID、来源、采集时间、数据类型、模拟/公开/真实标识、版本、生成方式、引用关系、人工状态和修改记录。

## 7. AI 与技术边界

只有 AI 处理文本理解、归纳、解释、生成等不确定任务；规则处理确定性校验，人工保留事实、合规、预算、发布和最终业务判断。

技术方案必须交代：

1. 输入、请求参数、鉴权、返回、解析、展示和日志；
2. 真实调用和固定演示模式的明显标识；
3. 模型返回的结构化 JSON 与解析失败处理；
4. API Key/Token 使用环境变量和 `.env.example`，不进浏览器或仓库；
5. 超时、额度、无效响应、重试和降级；
6. 模型/API 选择理由、价格、厂商特点和适用场景；价格与可用性要在交付时重新核对；
7. 数据保存、导入/导出与恢复方式；首版可用本地状态和 JSON 往返，不必先做数据库；
8. 有敏感事实或高风险表达时，未完成人工复核不得导出或发布。

若没有真实调用，只能称静态原型或演示流程；fixture、Mock、预置结果、页面可运行和 E2E 测试不能证明真实模型效果。

## 8. 验收标准矩阵

以下是规划包交给学生的标准。右列是学生完成后应提交的证据，不代表 Agent 本轮已经验证。

| 维度 | 学生应提交的最低验收证据 |
|---|---|
| 事实 | 学生经历、公开事实、模拟数据、AI 生成和推断分开标识 |
| 闭环 | 从输入到业务产物、人工复核、反馈和复测可完整演示 |
| 演示模式 | 无 API Key 也可跑通固定样例，页面持续显示“演示数据” |
| 真实调用 | 配置 Key 后至少一次成功调用、结构化解析和展示 |
| 失败路径 | 空输入、无效格式、超时、无效返回和调用失败提示清楚 |
| 可追溯 | 结论和产物可回查来源样本；引用关系不丢失 |
| 人工边界 | 能修改产物、确认/驳回风险并记录理由和版本 |
| 数据一致 | 导出再导入后项目内容、引用、状态和版本一致 |
| 评测 | 正常、异常、边界用例与 3 个以上 Bad Case 有改动和复测 |
| 工程 | 干净环境可安装、启动、测试、构建；README 命令可复现 |
| 页面 | 真实浏览器完成点击、输入、滚动、编辑、导出和失败流程 |
| 学生掌握 | 学生能讲清业务、数据、Prompt/规则、代码、调用、Bad Case、人工兜底，并现场改一处后重跑 |

不能用“接口返回 200”“构建成功”“静态截图”“固定样例跑通”中的任意一项代替整体通过。

## 9. 交付包与学生提交包

**Agent 本轮交付给学生：**

- 前置资料、学习顺序、工具小任务和完成标准；
- 完整 PRD、产品架构图、技术架构图与数据流；
- 可操作 UI/UX Demo；
- 学生执行计划、验收矩阵、测试用例和证据清单；
- 事实账本：已确认、规划中与 `Open`。

**学生落地后提交：**

- 源码与可访问仓库：README、依赖、启动方式、`.env.example`；
- 脱敏样本、字段说明、来源、时间和模拟边界；
- Prompt v1/v2、迭代理由、真实调用记录和失败样例；
- 自动测试、浏览器验收、评测记录、Bad Case 与复测；
- 关键截图、演示视频/脚本和现场答辩。

只有验收矩阵有真实证据后，才把对应能力写入简历；结果指标只写实际测得值。

## 10. 常见偏差

| 偏差 | 修正 |
|---|---|
| 从“做个 AI 工具”开始 | 从学生真实工作流和目标岗位反推问题 |
| 页面很多但没有业务产物 | 补齐人工复核、业务输出、反馈与复测 |
| Mock 冒充真实模型 | 明示演示模式，并单独验证真实调用 |
| 结论没有来源 | 为 Finding 和 Artifact 保存 source IDs |
| 技术栈堆砌 | 删除不直接解决核心场景的系统与框架 |
| 导师交成品让学生背 | 按 T1/T2/T3 调整脚手架，统一现场解释与修改门槛 |
| Agent 把“整体规划”做成代开发 | Agent 交四件套规划包，源码、真实调用和复测由学生完成 |
| PRD 完成就写进简历 | 等代码、调用、失败路径和学生讲解均验收后再写 |

## 11. 飞书落位与写后验收

完成态默认是学生可以照着执行的飞书规划子页面，不是已开发完成的产品。

1. 解析用户提供的学生主页/目标文档，核对正式姓名、标题、对象类型、父级、唯一性和当前修订。
2. 在唯一学生入口下创建或更新独立子页面；默认标题为 `姓名｜作品集产品方案｜项目名`。
3. 页面首屏先给可操作 UI/UX Demo 入口，再给当前规划阶段、下一行动和待确认项；正文按四步展开前置资料、完整 PRD、UI/UX Demo 与验收标准。Demo 入口优先展示不改变四件套责任边界，代码开发、真实调用与评测仍是学生后续任务。
4. UI/UX Demo 使用可访问链接或附件；源码仓库、README、样本、Prompt、测试和视频列为学生后续提交项，不把空链接或计划写成现有附件。
5. 写后重新读取标题、父级、唯一性、修订、目录、正文、附件、链接和关键块顺序；再检查学生端显示。
6. 通用面试、职业规划、课程、简历和其他子页面保持不变；没有唯一入口时停止写入。
