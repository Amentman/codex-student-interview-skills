# 修改并交付简历

## 结果定义

把用户给出的简历、批注、截图、群聊、飞书记录和本地知识库整理成一条可追溯证据链，在不编造、不越权删内容、不擅自换版式的前提下，交付可直接审阅或投递的简历。

先锁定三种模式：**诊断**只交付有依据的问题和建议，不改正文或生成文件；**文本修改**只改本次要点／段落，记录原文—改文—理由—证据并保护其余内容；**文件交付**才建立完整母版链、生成指定 Word/PDF 并完成真实查看器验收。不因诊断或文本请求自动生成、移动、删除文件。

## 必须调用的能力

- 内容证据、JD 映射和经历叙事：使用 `building-resume-interview-stories`。
- 涉及本机微信聊天、学员群、导师群或班主任对话：使用 `yichen-wechat-local-vault`，只做任务所需的定向读取。
- 交付 `.docx`：使用 `documents:documents`。
- 交付 `.pdf`：使用 `pdf:pdf`。
- 若用户给了飞书页面、表格或课程记录：优先用当前可用的 `lark-cli` 解析、读取和回读；不要用截图代替可读取的正文。

## 按模式执行的总流程

三种模式均须读取相关来源、核对事实与冲突，保护原文。下图为文件交付全流程：诊断止于事实判断与建议；文本模式做到授权要点改写与内容读回；只有文件模式执行布局母版、Word/PDF派生、目录清点与实机渲染。

```text
当前请求与验收口径
  → 锁定学生、方向、源简历、受保护版式
  → 定向读取本地文件 / 微信 / 飞书 / 老板知识库 / JD
  → 建来源清单、事实账本、冲突表、原文保留表
  → 形成共享事实母账和各方向表达策略
  → 逐条改写并记录原文—改文—理由—证据
  → 每个方向形成唯一内容与布局母版
  → 派生批注 Word 与干净 PDF
  → 机器检查 + WPS/Word 实机检查 + PDF 实际渲染检查
  → 清点最终目录、旧版去向和 Open 项
```

不能因赶交付跳过适用的取证和原文保护；文件交付不能跳过真实渲染验收。文件存在、导出成功、页数显示 `1/1` 都不等于完成。

## 第一道门：锁定本次任务

开始改写前明确：

1. 学生正式姓名及唯一学生目录。
2. 本轮权威源简历及其日期/版本；截图中的文件名要和真实文件对应。
3. 目标方向或具体 JD。两个方向必须是两条独立交付链，共用事实母账但不能混用方向表达。
4. 本轮修改范围：内容、批注、版式、文件格式、页数、清理范围分别是什么。
5. 受保护对象：原有版式、完整实习/项目、原稿、其他方向、飞书页面等。
6. 验收口径：是否完整饱满单页、是否保留原版式、目标应用是否为 Mac WPS/Word、最终应有几个文件。

出现以下任一情况，停止改写，只继续做只读核对：学生或源简历不唯一；方向不明确；文件名与正文身份冲突；多个版本事实冲突且无法裁决；用户要求继承某版式但基线文件缺失。

## 第二道门：按顺序建立证据链

只要用户说“结合我的知识库/群聊/飞书/授课记录”，就必须实际读取，不得只在回复中声称“已结合”。执行顺序：

1. **当前请求、截图和批注**：提取修改范围与验收条件；截图只证明当时看到的界面，不证明当前文件内容。
2. **本地学生材料**：源简历、历史简历、作品、项目附件和已有交付，先按时间和方向排版本。
3. **微信证据**：定向查学生本人、学员群、班主任对话、导师群中与姓名、简历版本、关键经历、数字、修改意见相关的消息；记录会话、时间和消息定位。
4. **飞书证据**：读取学生主页、授课文档、简历信息表、模拟面试/复盘、任务卡、课程记录及附件；记录 URL/token、标题、对象类型、修订号或表格位置。
5. **老板知识库与授课材料**：按目标岗位、经历类型和问题关键词检索；读取知识单元的来源、证据等级、验证状态和质量状态。它们只支持方法、岗位逻辑和术语，不自动证明学生做过。
6. **JD 与公司材料**：只用于岗位要求、业务背景和关键词映射，不得反向制造个人经历。

详细检索与隐私规则见 [多来源取证与可追溯性](references/source-intake-and-traceability.md)。案件开始后使用 [案件工作底稿模板](references/case-workbook-template.md)，不要凭记忆直接写简历。

## 来源裁决规则

“最新文件”不自动胜出，按要证明的事实类型裁决：

| 要证明的内容 | 优先证据 | 不能替代它的材料 |
| --- | --- | --- |
| 本轮范围与交付标准 | 用户当前明确要求 | 旧聊天、旧交付说明 |
| 学生本人做过什么 | 学生确认 + 原始产物/过程材料 + 一致的源简历 | JD、知识库、导师示例 |
| 数字、时间、分母、归因 | 原始记录或学生可解释的明确确认 | 只出现过一次的数字、团队总指标 |
| 岗位方法与术语 | 经验证知识库、课程、官方 JD | 把方法论写成学生实践 |
| 版式基线 | 用户指定或最后确认可用的源文件实际渲染 | 新模板、截图猜测 |
| 修改建议 | 当前批注、导师意见、用户口径 | 自动变成删除授权 |

冲突时建立冲突表，保留两种说法、各自来源和建议裁决。不能证明的一律标为 `Open`，用保守表达或暂不写，不暗中“择优”。

## 第三道门：按模式保留追溯记录

来源与事实冲突记录用于所有模式；诊断记录被判断要点的原文定位即可。文本修改建立本次被改要点的原文保留记录，不要求无关段落的全量矩阵。文件交付建立以下四张内部工作表；不必全部交给用户，但必须可追溯：

1. **来源清单**：来源类型、标题/会话、日期、定位、版本、用途、是否已读。
2. **事实与冲突账本**：`Confirmed / Externally verified / Inferred / Knowledge supplement / Open`，并记录证据定位和可写边界。
3. **原文保留表**：源简历每段经历/每个要点保留精确定位、逐字原文或可回读引用，并拆出其中的关键动作；处置为“保留、改写、合并、删除”，合并或删除必须写原因和授权依据。
4. **文件血缘表**：源文件 → 方向母版 → 批注 Word → 干净母版 → PDF；每个文件记录方向、母版 ID、日期和最终状态。

没有原文保留表，不得声称“没有删内容”；没有文件血缘表，不得声称 Word/PDF 同源。

## 内容修改合同

1. 先建立所有方向共用的事实母账，再分别做方向表达；同一事实不能在不同版本中产生互相冲突的责任或数字。
2. 使用“问题/需求 → 个人动作 → 产出/验证 → 结果”组织要点，但不在简历中显示方法标签。
3. 用户说“压缩开头”，只压背景句、概述句或重复总述；不能把整段实习、操作步骤、验证逻辑和结果一起压掉。
4. 批注意味着需要判断和说明，不等于删除授权。导师建议和学生反馈要翻译成具体改动，而不是机械照抄。
5. 压缩顺序：重复话 → 空话 → 可合并背景 → 与目标方向弱相关的低价值细节。优先保留责任边界、关键动作、判断过程、交付物、验证方法和可解释结果。
6. `0-1`、Evaluation Harness、Prompt、Workflow、RAG、A/B Test 等术语，只有证据证明学生确实参与且能解释时才写；否则改成真实动作或列为 Open。
7. 个人实践、课程项目、导师示例和未来作品集不能改写成公司实习成果。
8. 没有可信数字时，用覆盖范围、产物、流程改变、评审结论或决策支持，不补造准确率、CTR、GMV、转化率或用户量。
9. 老板知识库用于校准“什么是好表达”和岗位逻辑；不把知识库案例、课程答案或其他学生经历复制进本人的简历。

完整规则见 [证据与内容边界](references/evidence-and-content.md)。

## 红字和批注合同

- 只把真正变化的文字标红，不把整段原文都标红。
- 批注挂到对应修改范围，写清“为什么改、解决什么问题、还有什么待确认”；不在正文另加一页内部说明。
- 批注数量和红字处数由实际改动决定，不机械追求固定数。截图中的 `6 条批注/19 处红字` 等数字只可作为该个案的历史验收证据，不能成为所有简历的默认指标。
- 若用户要求保留完整经历，批注不得通过删掉正文来“减少意见”。

## 文件交付合同

每个方向必须拥有唯一母版链：

```text
该方向权威源 + 共享事实母账
  → 内容与布局母版
      → Word 批注版（完整正文 + 红字 + 真实批注）
      → 干净母版（同正文/同布局，无批注/红字）
          → PDF 可投递版
```

两方向通常交付四个文件：每个方向一份批注 Word 和一份可投递 PDF。数量以用户本轮要求为准；不得因为曾经交付四个就强制所有任务四文件。

- 用户只让改内容时，继承源文件页边距、表格、栏位、标题层级、字体体系和视觉结构，不擅自换版式、增加“求职方向”栏或使用斜体。
- Word 与 PDF 必须来自同一方向同一母版，不可独立复制重排。
- 最终目录只放本轮官方交付。原稿和中间母版不混入；旧版只有在用户明确要求清理且来源已确认时，才移到目录外可恢复备份或废纸篓。
- 不知道来源或是否仍需保留的旧文件，不得删除或移动。

详见 [Word/PDF 交付规约](references/word-pdf-delivery.md)。

## 真实验收合同

用户要求“完整饱满的一页”时，必须同时满足：

1. 经实际打开后，Word 与 PDF 都是完整一页，不是只靠页数元数据判断。
2. 正文进入页面下部，底部没有明显半页空白；同时字号、行距和留白仍可读。
3. 完整实习、项目和证据链未因凑一页被过度删减。
4. Word 与 PDF 的模块、正文、日期、数字、主要换行和对齐看起来是同一份简历。
5. Word 在目标 Mac WPS/Word 中检查批注、分页、字体、边框和超链接；PDF 在真实查看器/渲染图中检查页面密度、截断、红字和注释。
6. 无意外斜体、隐藏文字、字体替换、评论遮挡、蓝色选中高亮或 PDF 审稿痕迹。
7. 正文同一要点的首行和续行字号、字体、字重和行高一致；不得出现局部文字突然变大、PDF 回退成宋体、续行基线错位等明显排版错误。

机器检查使用本 Skill 的 `scripts/inspect_delivery.py`，同时启用 Word 段内混合字号和 Word/PDF 字体字号漂移检查；它不能替代 WPS 和 PDF 的视觉检查。详见 [验收合同](references/qa-contract.md)。

## 完成门

仅检查本次模式的适用项；Word/PDF、布局、目录、批注与实机要求只用于实际文件交付。诊断不因没有目标JD或文件母版而暂停；涉及目标匹配时注明其缺项。文本模式验事实、原文保留和本次改文，不称文件交付完成。以下适用项任一存在，不得说“完成”：

- 没有实际读取用户点名的知识库、微信或飞书来源。
- 学生、源简历、目标方向或版式基线不唯一。
- 关键责任/指标仍冲突，却被写成确定事实。
- 原文有要点被删但没有原因和授权依据。
- Word/PDF 不是同母版，或未能证明文件血缘。
- 用户要求单页时，任一真实查看器中不是单页、明显稀疏或出现截断。
- 同一正文要点内出现未经设计的字号突变，或 PDF 使用 Word 中不存在的正文中文字体/字号而未复核。
- 批注 Word 没有真实批注/红字，或 PDF 带红字/批注/内部备注。
- 用户要求只留最新版时，最终目录仍混有测试稿/旧终版；或旧文件来源不明却被擅自处理。

## 最终回报格式

按本次模式报告用户可核验的结果：诊断给问题与建议，文本给改文和证据；下面文件、查看器和目录项仅用于文件模式。

- 最终交付文件及每个文件的方向和用途。
- 实际读取的来源类别，以及哪些内容仍是 `Open`；不暴露无关隐私和原始数据库信息。
- 修改策略：保留了什么、压缩了什么、改了哪些术语/方向表达。
- Word/PDF 的真实查看器、页数、纸张、密度、无斜体/无审稿痕迹、同源一致性验证。
- 最终目录文件数量、旧版本去向，以及通过备份清单/读回核对证明的可恢复性。

不要用“已导出”“脚本通过”或生成步骤代替最终证据。
