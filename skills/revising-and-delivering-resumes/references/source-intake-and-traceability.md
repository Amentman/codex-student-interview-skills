# 多来源取证与可追溯性

本文件用于用户要求结合本地知识库、微信、飞书、授课记录、多版简历或历史批注的场景。目标不是“读得越多越好”，而是让最终简历的每条重要事实都能回到正确来源。

## 1. 先写检索问题

在打开大量资料前，列出本轮需要回答的问题：

- 哪个文件是权威源简历？哪一个版本只供参考？
- 学生的正式岗位、公司、时间和个人责任是什么？
- 哪些数字的定义、时间、分母、基线和归因已确认？
- 导师具体建议改哪一句、压缩哪一部分、保留什么？
- 两个方向共享哪些事实，分别强调什么能力？
- 哪些内容是教学方法、未来项目或外部岗位要求，不是学生经历？
- 本轮要继承哪个版式，最终应交付哪些文件？

所有检索都围绕这些问题进行。不要为了“全面”盲目导出全部聊天或知识库。

## 2. 本地文件

1. 用文件名、正文姓名、修改时间和目录共同锁定学生，不能只凭文件名。
2. 列出所有候选简历和交付物：文件路径、格式、修改时间、正文姓名、目标方向、是否含批注、页数、用途。
3. 读取正文和文档属性；截图只作为视觉/验收线索，不代替真实文件。
4. 找到用户指定或最后确认的版式基线，记录纸张、页边距、表格、字体、字号、行距、段前后、边框、链接和照片。
5. 中间文件、旧终版和原稿分别标记；未确认前不移动、不覆盖、不删除。

## 3. 微信：定向读取，不扩大隐私暴露

使用 `yichen-wechat-local-vault` 的既定流程：

1. 先检查本地库状态和可用能力，不输出密钥、原始数据库路径或无关联系人信息。
2. 用学生正式姓名搜索联系人和群聊，确认唯一会话；同名或多个群时先做只读比对。
3. 优先搜索姓名、`简历`、方向名、公司名、项目名、关键数字、`导师`、`修改`、`确认`、`发你` 等任务关键词。
4. 再按命中时间段读取上下文，至少覆盖：学生本人消息、班主任/交付老师消息、导师意见、文件发送记录。
5. 每条使用到的证据记录：会话类型、会话显示名、发送者角色、时间、消息摘要、附件名或消息定位。最终简历工作底稿只保存必要摘要，不复制整段无关聊天。
6. 群里他人的案例、老师举例、推测、尚未得到学生确认的数字，不进入 `Confirmed`。
7. “发了新简历”只能证明版本存在；必须读取对应文件，不能凭文件发送消息推断正文。

若会话身份不唯一、附件缺失、关键消息被撤回或无法定位，标为 `Open`，不补猜。

## 4. 飞书：先 inspect，再精确读取

默认使用已配置的 `lark-cli`，并遵循对应飞书技能/命令帮助：

1. 对 URL 先做对象解析或 `drive +inspect --as user`，记录标题、类型、token、父级和修订信息。
2. 文档优先用 `docs +fetch` 获取 outline/关键词/目标 section；需要块定位时再读取结构/XML，不用截图 OCR 代替正文。
3. 表格先取 workbook/sheet 信息，再读取指定区域；记录 sheet 名和单元格范围。
4. Base 先 inspect schema，再读与学生唯一记录对应的字段；Wiki URL、doc token、base token 不混用。
5. 授课文档、学生准备版、模拟面试复盘、简历信息表、任务卡分别承担不同证据角色：
   - 简历附件/信息表：身份和学生自填事实线索；空字段不是事实。
   - 授课记录：课程中讨论过什么，不自动证明学生完成了什么。
   - 模拟面试复盘：能暴露责任、数字、过程证据缺口；导师示范答案不是学生经历。
   - 任务卡/未来项目：是计划，完成前不能写成成果。
6. 记录 URL/token、标题、对象类型、修订号、章节/Block ID 或表格坐标；有附件时记录附件名和可访问状态。

只读取本轮相关页面。没有用户授权时，不把内部审计或简历草稿写回学生可见飞书页面。

## 5. 老板知识库和授课素材

知识库解决“怎么判断、怎么表达、岗位真正看什么”，不是替学生补经历。

1. 在当前配置的知识库根目录，用 `rg` 按岗位、行业、经历类型、问题词和术语检索；优先知识单元，不先通读整库。
2. 对命中的单元读取元数据：source/source_id、evidence_level、verification_status、quality_status、主题和正文。
3. `user_approved` 或已验证内容可作为方法依据；`needs_review`、自动抽取、口语歧义或来源不清的内容只能作为检索线索。
4. 知识库观点可用于：
   - 判断岗位期待和关键词；
   - 识别简历空话、职责堆砌和团队结果冒领；
   - 选择叙事结构、项目粒度和信息优先级；
   - 校准一页简历中教育/经历/项目/技能的密度。
5. 知识库不能用于：
   - 证明学生参与过某流程或技术；
   - 复制其他学生的案例、数字或成果；
   - 把课程中讲过的 0-1、评测、Prompt、RAG 等写成学生已做经历；
   - 用“行业一般如此”补齐具体公司事实。

底稿中记录知识单元 ID、验证/质量状态和它影响了哪条修改策略。

## 6. 来源矩阵

每个候选事实至少一行：

| claim_id | 候选表达 | 类型 | 来源定位 | 时间/版本 | 责任与数字是否完整 | 状态 | 最终处置 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| C01 | 某场景完成某动作 | 个人动作 | 文件页/段；聊天+时间；飞书块/单元格 | 日期 | 是/否 | Confirmed/Open | 写入/保守改写/不写 |

“来源定位”不能只写“微信”“飞书”“知识库”，必须精确到以后可复查的位置。

## 7. 冲突处理

| 冲突类型 | 处理 |
| --- | --- |
| 两份简历岗位名称不同 | 查学生确认、公司材料/原始附件和时间线；未确认则保留真实宽口径，不擅自改成更高级职位 |
| 学生和导师对责任范围表述不同 | 找原始产物/过程证据；无法裁决则降低责任动词并列 Open |
| 同一指标多个版本 | 不取最大值；核对定义、分母、时间、基线、个人归因 |
| 飞书任务说“要完成”，简历说“已完成” | 任务是计划，不证明完成；需要完成记录或学生确认 |
| 知识库说岗位应具备某能力，学生没有证据 | 作为差距或未来补强，不写进已完成经历 |
| 截图显示某版本合格，当前文件不同 | 截图只保留为历史验收线索，重新检查当前文件 |

## 8. 停止条件

遇到下列情况，不进入成稿：

- 学生、方向、源简历或版式基线不唯一。
- 关键附件在聊天里出现但本地/飞书无法读取。
- 个人责任、指标或上线状态存在直接冲突。
- 用户要求继承历史版本，但截图/链接与当前文件无法建立对应关系。
- 需要清理旧文件，但旧文件来源和用途无法确认。

先完成其余可确认内容，把阻塞压缩成最小问题交给用户。
