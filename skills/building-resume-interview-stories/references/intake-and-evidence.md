# Intake and Evidence

Use this reference before explaining a project, researching a company, writing resume claims, or preparing interviews.

## 1. Normalize the Material

Build this internal inventory:

| Category | Capture |
| --- | --- |
| Company and role | Legal/display name, team, title, dates, location |
| JD | Responsibilities, required skills, business goal |
| Background | Who had what problem and why it mattered |
| Candidate actions | Exact tasks, decisions, code, analysis, documents, coordination |
| Process | Inputs, steps, outputs, controls, handoffs |
| Results | Metrics, artifacts, coverage, adoption, decisions supported |
| Tools | Languages, libraries, platforms, methods |
| Boundaries | Team contribution, mentor support, prototype/production status |
| Reflection | Learning, interest, next direction |

Correct obvious spelling and grammar, but preserve uncertain meaning as an Open item.

## 2. Create the Fact Ledger

| Claim candidate | Label | Evidence | Resume-safe wording | Missing proof |
| --- | --- | --- | --- | --- |
| Example: built an automated pipeline | Confirmed / Inferred / Open | User statement, code, artifact | Participated in building... | Ownership and deployment status |

Apply these labels strictly:

- **Confirmed:** user explicitly states it or a supplied artifact demonstrates it.
- **Externally verified:** credible public source confirms company/industry context.
- **Inferred:** likely but not stated.
- **Knowledge supplement:** explanatory domain content.
- **Open:** a missing fact that changes the story.

Resume claims require Confirmed evidence. External facts remain company context. Inferences need confirmation. Knowledge supplements belong in learning notes, not first-person claims.

## 3. Calibrate Ownership

| Evidence supports | Safe verbs |
| --- | --- |
| Followed instructions or handled a subtask | assisted, supported, completed, tested |
| Implemented a defined module | implemented, developed, built the module |
| Helped shape the approach | participated in designing, helped define, contributed to |
| Owned end-to-end delivery | owned, designed and delivered |
| Coordinated people and outcomes | led, drove, managed |

Do not infer a higher level from job title, tool sophistication, or project importance.

Confirm these common boundary questions:

- Did the candidate speak directly with the stakeholder or receive relayed requirements?
- Did they write the core logic, integrate modules, test, or only observe?
- Was the output a proposal, prototype, internal tool, production system, or adopted workflow?
- Which result was measured, and by whom?
- Which parts existed before the candidate joined?

## 4. Reconstruct the Project

Use this model:

`Actor with problem → raw input → candidate intervention → output → quality control → downstream use → result`

Produce a one-sentence definition:

> I helped [actor] turn [difficult/manual/unclear input] into [usable output] by [main intervention], so that [business use/value].

Then explain one real or clearly marked illustrative example. Do not invent an example and present it as real.

## 5. Research Company Context

Use sources in this order:

1. Government, regulator, registry, filing, or exchange.
2. Company website, official newsroom, official job page.
3. Reputable financial or industry reporting.
4. Established databases and professional profiles.
5. Community posts only as leads, never as sole proof for important facts.

For each fact record the source, publication/access date, and whether it is stable or dynamic.

Stable examples: legal name, founding date, registered business.
Dynamic examples: funding, headcount, assets, rankings, product count, hiring, strategy mix.

Do not research or expose confidential internal information.

## 6. Decide Whether to Ask

Ask one focused question when the answer changes:

- ownership level;
- the central business outcome;
- whether a claimed feature existed;
- prototype versus production status;
- the target role and therefore the narrative angle.

Do not block on missing cosmetic details. Draft conservatively and list them for later verification.

## 7. RED Baseline Checks

The workflow fails if it:

- rewrites jargon without teaching the candidate what the project did;
- generates a technical resume immediately after the user asks for plain language;
- states PIT, configuration, snapshots, deployment, or stakeholder ownership without confirmation;
- invents an efficiency percentage because the result lacks metrics;
- generates dozens of interview answers before the resume claims are stable.

Stop and return to the fact ledger when any failure appears.
