# 学生目录与选岗表写回

## 目标解析

使用当前可用的 `lark-cli` 只读解析用户提供的 Wiki URL，或在已确认的 Wiki 空间中定位学生正式姓名。先用 `wiki +node-get` 核对 `title`、`obj_type`、`node_token`、`obj_token` 和 `parent_node_token`，再用 `wiki +node-list` 读取学生目录的直接子节点。

目标必须同时满足：

- 父级是该学生正式姓名目录；
- 标题唯一匹配 `选岗/投递表-【姓名】`；
- `obj_type=bitable`；
- 能解析出唯一 Base token（Wiki 节点的 `obj_token`）。

不要把 Wiki node token、文档 token、Base token 和 table ID 混用。多个同名学生目录、多个目标表、缺少父级关系或无法确认学生身份时停止写入。

## 表结构读取

用 `base +table-list` 读取 Base 中的表；只有一张表时才可继续，多个表必须按真实标题/用户指定表确认。用 `base +field-list` 读取字段和选项，不按旧模板臆测。当前已核验过的示例表包含：`公司`、`投递岗位`、`批次`、`城市`、`届别/学历要求`、`校招官网链接`、`专岗详情链接`、`匹配度`、`匹配证据`、`主要缺口`、`核验时间`、`截止时间`、`优先级`、`相关性`、`企业性质`、`所属行业`、`投递进度`、`面试状态`、`笔试状态`、`求职备注`、`备注` 和附件字段。实际写入以读回的字段为准。

用 `base +record-list` 分页读取已有记录，保留与本次无关的字段和行。新岗位只填有证据的字段；`JD截图` 没有真实截图时留空，不伪造附件。

## 写入与幂等

写入前形成计划：目标 Base/table、待新增岗位、每条职位唯一键、将写入字段和预计新增数。默认用 `base +record-upsert` 逐条创建新行；已有唯一键跳过，除非用户明确要求更新。批量写入失败时只重试未确认批次，不重复提交已确认行。

把学生目录 `node_token`、目标 Base/table、规范化城市/方向/届别、已见职位键和公司计数一起保存在当前对话状态。用户要求“更多”时继续搜索未覆盖的官方来源；状态缺失时停止，不把其他学生或其他筛选条件的结果混入本次写回。

岗位字段建议映射：

| 推荐结果 | 多维表字段 |
|---|---|
| company_name | 公司 |
| job_name | 投递岗位 |
| batch | 批次（只有匹配现有选项时写入） |
| city | 城市 |
| education | 届别/学历要求 |
| deliver_url | 专岗详情链接 |
| official_campus_url | 校招官网链接 |
| match_score / match_level | 匹配度 |
| confirmed_evidence + JD evidence | 匹配证据 |
| gaps | 主要缺口 |
| updated_at / checked_at | 核验时间 |
| deadline | 截止时间 |
| priority | 优先级 |
| company_nature | 企业性质 |
| industry | 所属行业 |
| note / Open | 备注 |

没有独立“网申时间”字段时，不要把开放时间误写进“截止时间”；将未映射的时间信息放入备注并标明来源，或留为 `Open`。

## 写后验收

重新读取目标表并核对：写入对象仍是目标学生目录下的唯一 bitable；新增数量与计划一致；新岗位的公司、岗位、城市、链接和证据字段可读；没有职位唯一键重复；本次推荐集合中每家公司不超过 3 条；原有记录数量和内容未被删除或覆盖。把跳过、失败、权限错误、未核验字段和过期岗位分别报告。日期缺失、解析失败或时区不明时不要伪造核验时间。
